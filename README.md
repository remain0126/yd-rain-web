# 영덕군 강우상황 모니터링

영덕군 관내 읍면 강우량과 119안전센터별 위험도를 모바일에서 보는 PWA.
GitHub 연동으로 Netlify에 자동 배포됩니다.

## 구조

```
yd-rain-web/
├─ netlify.toml
├─ package.json
├─ netlify/functions/
│   ├─ _scrape.js            # 영덕군청 페이지 파싱 (파싱만)
│   ├─ _history.js           # 시간별 이력 누적 + 최근 1/3/12시간 창 계산
│   ├─ _tiers.js             # 강우 단계 기준 (극한호우 포함 4단계)
│   ├─ _build.js             # 파이프라인: 긁기 -> 이력 병합 -> 창 계산 -> 판정
│   ├─ _warning.js           # 기상청 특보 조회 (API 2종 + 페이지 폴백)
│   ├─ _push.js              # 웹푸시 공용: 구독 보관, 발송
│   ├─ _logbook.js           # 운영기록 일별 집계 -> GitHub 커밋 (logs/)
│   ├─ rainfall.js           # 사용자 접속 응답 (/api/rainfall)
│   ├─ warning.js            # 특보 조회 (/api/warning)
│   ├─ watch.js              # 1분 감시 + 알림 발송 (/api/watch)
│   ├─ push.js               # 구독 등록/해지/확인/시험 (/api/push)
│   ├─ logs.js               # 운영기록 조회 (/api/logs)
│   ├─ watchdog.js           # 5분마다 감시 생존 확인 + 자가복구 (/api/health)
│   ├─ scheduled-refresh.js  # 5분마다 백그라운드 수집 호출
│   ├─ refresh-background.js # 실제 수집 (최대 15분까지 실행 가능)
│   └─ diag.js               # 진단용 (/api/diag)
└─ public/                   # 프론트엔드 (PWA)
```

## 두 개의 주기

- **수집** — Netlify 예약 함수가 5분마다, 감시가 1분마다 백그라운드 수집을 건다.
  군청 응답이 1~2분 걸릴 때가 있어 앞 건을 기다리지 않고 동시 3건까지 던진다.
  늦게 출발한 것이 먼저 도착할 수 있으므로, 저장 직전에 더 새로운 자료가
  이미 저장됐는지 확인하고 오래된 것은 버린다.
- **감시/발송** — 외부 스케줄러(cron-job.org)가 `/api/watch`를 1분마다 부른다.
  그쪽이 죽으면 `watchdog`이 5분 안에 대신 돌린다.

## 핵심 1: 자정을 넘는 누적 계산

영덕군청 페이지는 **당일 01~24시**만 제공하고 어제의 시간별 값은 주지 않는다
(전날누적 = 어제 하루 총합 하나뿐). 그래서 새벽 2시에 12시간 누적을 구하려면
어제 15~24시 값이 필요한데 그 정보가 원본에 없다.

→ 수집할 때마다 **시간별 값을 Blobs에 누적 저장**하고,
`_history.js`가 그 이력을 이용해 **연속된 시간축**으로 창을 계산한다.
따라서 23시부터 쏟아진 비도 자정을 넘겨 정확히 3시간/12시간 누적에 반영된다.

이력은 48시간치만 보관한다.

## 핵심 2: 창의 기준점은 시계다

예전에는 창의 끝을 "표에서 값이 들어있는 마지막 칸"으로 잡았다. 두 가지가 잘못됐다.

- 군청 표가 갱신을 멈추면 몇 시간 전 비를 계속 현재 상황으로 판정했다.
  자료 나이(`stored_at`)는 *우리가 언제 긁었나*라서, 군청이 옛 표를 계속
  내주면 정상으로 보였다.
- 비가 그쳐 빈칸이 생기면 기준이 과거에 못 박혀 단계가 내려가지 않았다.
  상황 종료 알림이 안 나가고 반복 알림이 계속됐다.

지금은 **한국시각 기준 직전 완료 시각**을 창의 끝으로 삼는다. 비가 그치면
옛 값이 창 밖으로 밀려나며 저절로 단계가 내려가고, 표가 멈추면 창이 비어간다.
표가 시계보다 얼마나 뒤처졌는지는 `table_lag_h`로 따로 알린다
(2시간 이상이면 화면에 "군청 표 N시간 정체"가 뜬다).

진행 중인 시각은 아직 쌓이는 중이라 누적 창에 넣지 않고, 1시간 판정에서만
직전 완료 시각과 큰 쪽을 쓴다. 시간당 72mm 같은 즉시 기준을 놓치지 않기 위함이다.

## 결측 처리

없는 칸은 **0으로 세지 않고 결측으로 센다.** 없는 숫자를 지어내면 헛출동으로
이어지므로, 수치는 실측 합계만 담고 결측 사실을 화면에 그대로 표시한다
(`window_complete_3h` / `window_complete_12h` → "일부결측").

단, 군청 표는 비가 오지 않은 시각을 0이 아니라 빈칸으로 두는 경우가 있다.
**뒤쪽에 값이 있으면 앞의 빈칸은 무강우로 확정**한다. 이렇게 하지 않으면
매일 결측 표시가 떠서 곧 아무도 보지 않게 된다.

## 강우 단계 기준 (`_tiers.js`)

| 단계 | 발령기준 | 조건 |
|---|---|---|
| 극한호우 | 극한호우 | 3시간 90mm↑ **AND** 1시간 50mm↑, 또는 1시간 72mm↑ 즉시 |
| 호우경보 | 호우경보 | 3시간 90mm↑ 또는 12시간 180mm↑ |
| 호우주의보 | 호우주의보 | 3시간 60mm↑ 또는 12시간 110mm↑ |
| 관심단계 | 관심단계 | 3시간 30mm↑ 또는 12시간 60mm↑ |

기준을 바꾸려면 `_tiers.js`만 수정하면 된다 (프론트는 서버에서 기준표를 받아 표시).

## 배포

GitHub 저장소에 파일을 올리면 Netlify가 자동 배포한다.
(Netlify Blobs는 GitHub 연동 배포에서만 동작한다 — 드래그 배포로는 크래시 남)

## 확인

- 사이트: `/`
- 데이터 API: `/api/rainfall` (JSON)
- 강제 최신: `/api/rainfall?fresh=1`
- 진단: `/api/diag`

## 구독 명단

사람마다 키를 따로 쓴다 (`subs/<주소해시>`).

예전에는 명단 전체를 배열 하나에 담아두고 발송·확인·정리가 모두 그 배열을
통째로 읽고 고쳐 다시 썼다. 누가 [확인]을 누른 순간에 발송이 겹치면 확인
기록이 통째로 덮여 알림이 다시 울렸다.

`@netlify/blobs` 8.x에는 조건부 쓰기(`onlyIfMatch`)가 없어 CAS로는 막을 수 없다.
사람마다 키를 나누면 애초에 겹치지 않는다. 예전 배열은 첫 읽기 때 자동으로
쪼개져 옮겨지고 지워진다.

새 코드에서는 `writeSubs`(통째 쓰기)를 쓰지 말고
`putSub` / `updateSub` / `updateAllSubs`를 쓴다.

## 주의

- 참고용 자료이며 공식 특보는 기상청 발표 기준을 따른다.
- 도입 초기에는 이력이 아직 쌓이지 않아 12시간 창이 불완전할 수 있다.
  화면에 "일부결측"이 표시되며, 수집이 12시간 이상 돌면 완전해진다.
- Netlify Blobs는 GitHub 연동 배포에서만 동작한다 (드래그 배포로는 크래시 남).
